# STRATEGY.md
last_updated: 2026-09-08

## Target Problem

Spring and Java knowledge is often learned in isolated pieces that do not demonstrate how to design and deliver a complete production-minded system. This project consolidates that knowledge into one coherent e-commerce application that a senior developer can use to demonstrate backend, frontend, database, and delivery skills.

## Approach

Build one end-to-end pet project with a strong database foundation, Clean Architecture boundaries, object-oriented design, and deliberately selected design patterns. Spring Boot provides the backend and Angular provides the frontend, while tests and operational evidence demonstrate that the architecture works beyond diagrams and abstractions.

## Audience

The primary user is a senior developer presenting practical Java and Spring capability to technical reviewers, with prospective clients as a secondary audience evaluating delivery competence.

## Success Metrics

- All approved requirements and acceptance criteria are implemented and demonstrable through the complete customer and administrator journeys.
- Automated backend, frontend, integration, and security tests pass through CI, with measurable quality thresholds defined during planning.
- The full application can be deployed through CI/CD and has verified observability and rollback procedures.

## Strategic Tracks

- **Architecture and domain mastery**: Apply Clean Architecture, OOP, purposeful design patterns, and rigorous relational database design without speculative abstractions.
- **Full-stack product delivery**: Deliver cohesive Spring Boot APIs and Angular user journeys as one independently testable system.
- **Engineering excellence**: Make testing, security, observability, CI/CD, deployment, and rollback evidence part of completion rather than follow-up work.

## Optional: Known Constraints

- The project is an individual practice build and should remain achievable without sacrificing architectural or verification quality.
- Design patterns must solve a named problem and earn their complexity; pattern count is not a success metric.

## Optional: Out of Scope

- Payment processing, promotions, reviews, wishlists, and capabilities not explicitly approved during requirements planning.
